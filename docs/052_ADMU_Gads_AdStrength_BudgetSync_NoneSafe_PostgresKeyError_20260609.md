# Google広告「広告有効性（充実度）」向上と予算配分エラー（Nullable / PostgreSQL KeyError）の解消

Google広告での広告評価向上対策と、クレジットカード有効化後に発生した予算自動・手動配分処理のバグについて、その原因と対策を記録します。

---

## 1. Google広告「広告の有効性（充実度）: 低い」問題の改善

### 課題
Google広告側で見出しや説明文の数が足りない、あるいは「ビジネス名」「サイトリンク（表示オプション）」などのアセットが設定されていないため、広告の配信効率（Ad Strengthスコア）が「低い」と判定されてしまう。

### 対策・実装
1. **アセットの自動生成およびキャンペーン紐付け (AdsClient / API)**:
   - キャンペーンを一括作成した際（`/api/campaigns/setup`）および広告文を適用した際（`/api/ad-copy/apply`）に、以下の処理を自動実行するように実装。
     1. クリニック情報から「クリニック名」を取得し、ビジネス名アセットを検索・新規作成して、Google広告キャンペーンへ紐付け。
     2. ランディングページのURLを元に、2本の予約用「サイトリンク」アセット（例: 「オンライン予約はこちら」「当院の特徴・メニュー」など）を自動生成し、キャンペーンへ紐付け。
   - 重複登録によるAPIエラーを防ぐため、事前に既存のアセットを `searchStream` クエリで検索し、あれば再利用、なければ作成する堅牢なフローを採用。
2. **直接編集エディタUIの導入 (フロントエンド)**:
   - AIが生成した見出し（最大15個）と説明文（最大4個）をその場ですぐに追加・編集・削除できるテキストボックス型のインタラクティブエディタを導入。
   - Google広告の文字数ルール（半角1文字・全角2文字換算で、見出し最大30文字、説明文最大90文字）に基づいた**リアルタイム文字数カウンター**を表示し、制限オーバー時は赤字などで警告。
   - 画面エディタで調整した最新の入力データが、Google広告（RSA）に直接反映されるようAPI定義を拡張。
3. **AI生成プロンプトとテンプレートの強化**:
   - 必ず見出しを15本、説明文を4本フルで、地域名や悩みなどの重要キーワードを組み合わせた形で見出しの最初の方に配置するようAIの指示を厳格化。
   - Gemini APIが使えない場合のフォールバックやA/Bテスト時のテンプレートも見出し15本、説明文4本フルに拡張。

## 2. 配信実績データ無しによる予算自動配分エラー（Nullableキャスト問題）

### 課題
支払いのトラブル等で配信が一時停止していたアカウントや新規登録されたばかりのアカウントにおいて、「AIで最適配分（自動予算配分）」を実行すると、Google Ads APIから返ってくる過去7日間の実績データ（CTR, CVR, 平均CPC, コストなど）がすべて `None` になる。
これに対し、バックエンドで数値キャスト処理 (`float()`, `int()`) を適用したことで `TypeError` が発生し、500内部サーバーエラーを引き起こしていた。

### 対策・実装
- `backend/ads_client.py` 内の `list_campaigns` と `get_performance_series`、および `backend/main.py` 内の `_run_ai_budget_allocation` にて、APIが返すメトリクス値をパースする処理を**Nullable安全（Null-safe）**に変更。
- 値が `None` の場合は例外をスローせず安全に `0` にフォールバックするよう変更し、未配信アカウントでもクラッシュせず正常に均等配分などの処理へ移行するようにした。

## 3. 本番DB（PostgreSQL）特有の KeyError（インデックスアクセス）の解消

### 課題
手動予算配分（`/api/budget/manual-allocate`）および月間総予算設定（`/api/budget/monthly-target`）の処理内にて、DBから取得したキャンペーンレコードから `google_campaign_id` を取り出す際、`row[0]` という数値インデックスでアクセスしていた。
開発環境の SQLite (`sqlite3.Row`) では問題なく動作するが、本番環境の PostgreSQL (`psycopg2` + `RealDictCursor`) では返されるレコードオブジェクトが Python の `dict` (辞書型) になるため、数値インデックスでのアクセス時に `KeyError: 0` が発生して適用処理がクラッシュしていた。

### 対策・実装
1. **キーによる列名指定アクセスへの統一**:
   - `row[0]` となっていた記述を、DBの型を問わず安全に動作する `row["google_campaign_id"]` に変更。
2. **非クラッシング（Non-crashing）構造への改善**:
   - Google広告への予算同期時に、DB内に残っていた過去のモックキャンペーン（`MOCK-` から始まるID）やデモ用キャンペーン等の存在しないIDが含まれていても、同期を安全にスキップするか、例外をキャッチして警告ログを出力し、**存在する正常なキャンペーンの同期をクラッシュさせずに処理を完了させる**堅牢な例外処理（ノンクラッシング構造）へ変更。

---

## ナレッジのまとめ・教訓
- **開発と本番のDB差異**: DBラッパーを使用する場合であっても、`fetchone()` が返すオブジェクトはライブラリ依存で SQLite は `Row` オブジェクト、PostgreSQL は `dict` になる。タプル形式のインデックスアクセス (`row[0]`) は避け、**列名指定キー (`row["col_name"]`) で一貫して記述すること**が必須である。
- **Google広告APIのNullability**: ライブ配信が開始される前のキャンペーンはあらゆるメトリクスが `None` になるため、APIからの戻り値の計算・パース処理は例外なく Nullable 保護を施すこと。
